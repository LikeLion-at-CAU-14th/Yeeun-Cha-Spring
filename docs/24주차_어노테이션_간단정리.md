# 24주차 어노테이션 간단 정리

> 아래 제목 하나씩 노션 토글 제목으로 사용하면 된다.

### `@RestController`

- HTTP 요청을 받는 Controller에 붙인다.
- 메서드가 반환한 객체를 JSON으로 보내준다.
- 이번에는 `OrderController`에 사용했다.

### `@RequestMapping`

- Controller의 공통 주소를 정한다.
- `@RequestMapping("/orders")`를 쓰면 주문 API 주소가 전부 `/orders`로 시작한다.

### `@PostMapping`

- POST 요청을 받는다.
- 새로운 데이터를 만들 때 사용해서 주문 생성에 사용했다.

```java
@PostMapping
```

### `@GetMapping`

- GET 요청을 받는다.
- 주문 목록이나 주문 한 개를 조회할 때 사용했다.

```java
@GetMapping("/{orderId}")
```

### `@PutMapping`

- 기존 데이터를 수정할 때 사용한다.
- 이번에는 주문의 배송정보 수정 API에 사용했다.

### `@DeleteMapping`

- 삭제 요청을 받을 때 사용한다.
- 이번 과제에서는 진짜 DB 데이터를 지우지는 않고 `deleted = true`로 바꿨다.

### `@RequestBody`

- Postman에서 보낸 JSON을 DTO로 바꿔준다.
- 이걸 안 붙이면 Body에 보낸 값을 DTO로 받지 못한다.

```java
@RequestBody OrderCreateRequestDto dto
```

### `@PathVariable`

- URL 안에 들어 있는 값을 가져올 때 사용한다.
- `/orders/1`에서 `1`을 `orderId`로 받을 수 있다.

```java
@PathVariable Long orderId
```

### `@Service`

- 실제 기능을 처리하는 Service 클래스에 붙인다.
- 주문 조회, 생성, 수정, 삭제 같은 로직은 Controller가 아니라 Service에서 처리했다.

### `@Transactional`

- DB 작업을 하나의 단위로 묶어준다.
- 주문 정보를 수정한 뒤 `save()`를 다시 하지 않아도 변경 감지로 DB에 반영됐다.
- 메서드 중간에 문제가 생기면 변경 내용을 되돌릴 수도 있다.

### `@Transactional(readOnly = true)`

- 조회만 하는 메서드에 사용한다.
- 데이터를 바꾸지 않는 메서드라는 것을 표시하고, 불필요한 변경 감지를 줄여준다.

### `@Entity`

- 이 클래스가 DB 테이블과 연결되는 JPA 엔티티라는 뜻이다.
- `Orders`, `Member`, `Product`에 붙어 있다.

### `@Id`

- 엔티티의 기본 키를 나타낸다.
- 보통 `id` 필드에 붙인다.

### `@GeneratedValue`

- ID 값을 DB가 자동으로 만들어 주게 한다.

```java
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

### `@Enumerated(EnumType.STRING)`

- Enum 값을 DB에 문자열로 저장한다.
- 배송 상태가 `PREPARATION`, `DEPARTURE`, `COMPLETED`처럼 저장된다.
- 숫자로 저장하는 것보다 DB에서 확인하기 편했다.

### `@Embeddable`

- 다른 엔티티 안에 포함해서 사용할 클래스에 붙인다.
- 이번에는 배송정보를 묶은 `ShippingAddress`에 사용했다.
- 별도의 ID는 필요하지 않았다.

### `@Embedded`

- `@Embeddable` 클래스를 엔티티 안에 포함할 때 사용한다.
- `Orders` 안에 `ShippingAddress`를 넣을 때 사용했다.
- 배송정보 테이블이 따로 생기는 것이 아니라 `orders` 테이블에 컬럼들이 들어갔다.

### `@ManyToOne`

- 여러 데이터가 하나의 데이터를 참조할 때 사용한다.
- 여러 주문이 한 명의 구매자를 가질 수 있어서 `Orders`의 `buyer`에 사용했다.

### `@OneToMany`

- 하나의 데이터가 여러 데이터를 가질 때 사용한다.
- 주문 하나에 여러 상품이 들어갈 수 있어서 `productOrders`에 사용했다.

### `@JoinColumn`

- 연관관계에서 외래 키 컬럼 이름을 정한다.

```java
@JoinColumn(name = "buyer_id")
```

- `orders` 테이블의 `buyer_id`로 구매자를 연결했다.

### `cascade = CascadeType.ALL`

- 부모를 저장할 때 연결된 자식도 같이 저장되게 한다.
- 주문을 저장할 때 연결된 `ProductOrders`도 같이 저장할 수 있었다.

### `@Column(nullable = false)`

- DB 컬럼에 `null`이 들어가지 못하게 한다.
- Soft Delete에 사용한 `deleted` 값이 반드시 존재하게 만들었다.

### `@Getter`

- getter를 직접 작성하지 않아도 Lombok이 만들어 준다.
- DTO나 Entity의 값을 가져올 때 사용했다.

### `@Builder`

- 객체를 만들 때 필드 이름을 보면서 값을 넣을 수 있다.
- 생성자보다 어떤 값이 들어가는지 확인하기 쉬웠다.

```java
Orders.builder()
        .buyer(buyer)
        .deliverStatus(DeliverStatus.PREPARATION)
        .build();
```

### `@Builder.Default`

- `@Builder`로 객체를 만들어도 필드의 기본값을 유지하게 한다.
- `productOrders`는 빈 리스트, `deleted`는 `false`로 시작하게 했다.

```java
@Builder.Default
private Boolean deleted = false;
```

### `@RequiredArgsConstructor`

- `final` 필드를 받는 생성자를 Lombok이 자동으로 만들어 준다.
- Repository나 Service를 생성자 주입할 때 사용했다.

### `@NoArgsConstructor`

- 아무 값도 받지 않는 기본 생성자를 만들어 준다.
- JPA가 엔티티 객체를 만들 때 기본 생성자가 필요하다.

### `@AllArgsConstructor`

- 모든 필드를 받는 생성자를 만들어 준다.
- 필드가 많으면 생성자가 길어질 수 있어서 보통 `@Builder`와 같이 사용했다.

### `@Test`

- 테스트할 메서드라는 것을 표시한다.

### `@DisplayName`

- 테스트 결과에 보일 이름을 정한다.
- 메서드 이름보다 한글 설명으로 보이게 할 수 있어서 결과를 확인하기 편했다.

### `@Mock`

- 실제 객체 대신 테스트용 가짜 객체를 만든다.
- 실제 DB를 사용하지 않고 Repository의 결과를 정할 수 있었다.

### `@InjectMocks`

- `@Mock`으로 만든 객체를 테스트할 Service에 넣어준다.

### `@ExtendWith(MockitoExtension.class)`

- JUnit에서 Mockito를 사용할 수 있게 한다.
- `@Mock`, `@InjectMocks`를 사용하는 테스트 클래스에 붙였다.

---

### 짧은 정리

- Controller 관련 어노테이션은 요청 주소와 HTTP 방식을 정한다.
- JPA 어노테이션은 Java 객체와 DB의 관계를 정한다.
- `@Transactional`을 붙이면 변경 감지와 롤백을 사용할 수 있다.
- Lombok 어노테이션은 생성자, getter, builder 같은 반복 코드를 줄여준다.
- 테스트에서는 Mockito 어노테이션으로 실제 DB 없이 Service 로직을 확인할 수 있다.
